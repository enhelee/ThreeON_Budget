# 보안 설계 — 실데이터를 팀원만 다루는 공개 URL (2026-09-09)

> 전제(사용자 결정): 합성 데이터가 아닌 **실제 예산·실적 데이터**를 쓰되, **팀원만** 접근해 업로드·수정한다. 인증은 **공용 비밀번호 1개**이며 수정 이력은 남아야 한다. 지금은 무료 클라우드, 최종은 사내 분리망.

## 1. 위협과 대응 한눈에

| 위협 | 대응 | 구현 위치 |
|---|---|---|
| 공개 URL로 누구나 접근 | 모든 앱 경로에 비밀번호 게이트. `/forecast`는 엣지(Caddy basic_auth), `/app·/api`는 앱 로그인 | `deploy/Caddyfile`, `budget_app/src/budget/auth.py`, `server.py AuthAuditMiddleware` |
| 비밀번호·연결문자열 유출 | 코드·Git·이미지에 없음. `.env`(gitignore)·Render 환경변수·Supabase 대시보드에만. 감사 로그 요약에서 `password` 키 제거 | `deploy/.env.example`, `.gitignore`, `.dockerignore`, `auth.audit_detail` |
| 실데이터 Git 업로드 | `*.db`·`data_*.csv`·`matched_*.csv`·모델·`checkpoint_data/`·`config/*.json` 전부 gitignore/dockerignore | 패키지 `.gitignore`, `forecast_app/.gitignore` |
| "누가 바꿨나" 추적 불가(공용 비밀번호) | 로그인 때 **작업자 이름** 필수 → 서명 쿠키에 저장 → 변경 API마다 `audit_log`(시각·작업자·메서드·경로·상태·요약) | `db.add_audit/list_audit`, 설정 탭 「변경 이력」 |
| 세션 탈취·위조 | itsdangerous 서명(SECRET_KEY)·만료(SESSION_HOURS) 쿠키, HttpOnly·SameSite=Lax·Secure(https) | `auth.AuthConfig` |
| 전송 구간 도청 | Render/사내 프록시 HTTPS 종단, `COOKIE_SECURE=1` | `render.yaml`, `docker-compose.yml` |
| 완료 연도 수치 변조 | 연도 마감(잠금) — 변경 API 423 차단 | `server._guard_unlocked`, `year_lock` |
| 원자료 훼손 | 업로드 원본은 DB에 행 단위 흡수 후 임시파일 삭제, 원본 표(`plan_row`·`erp_row`) 불변, 모든 수정은 지시 테이블(override·biz_edit…)에 기록 → 이력 삭제 시 원복 | 기존 설계(MASTER §3) |
| 클릭재킹·MIME 스니핑 | `X-Frame-Options SAMEORIGIN`, `X-Content-Type-Options nosniff`, `Referrer-Policy` | `Caddyfile header` |
| DB 대시보드 침해 | Supabase 계정 2단계 인증, DB 비밀번호 32자, IP 제한(유료) 대신 pooler+SSL | 운영 절차(배포가이드 §1.2) |

## 2. 인증 흐름(budget_app)

```
브라우저 ─ GET /app/ ─▶ index.html (정적, 데이터 없음)
        ─ GET /api/auth/status ─▶ {enabled:true, logged_in:false} → 로그인 오버레이
        ─ POST /api/login {password, name} ─▶ 비밀번호 비교(hmac.compare_digest) → Set-Cookie budget_session=서명({op:name})
        ─ /api/* (쿠키) ─▶ 미들웨어 검증 → request.state.operator = name
        ─ POST/DELETE ─▶ 응답 후 audit_log INSERT (operator, method, path, status, 요약)
        ─ 401 login_required ─▶ 프론트가 오버레이 재표시
```
- `APP_PASSWORD`가 비어 있으면 인증이 꺼지고 작업자는 `local`로 기록된다(사내망 개발용). **공개 배포에서는 절대 비우지 않는다**(entrypoint가 경고).
- 실패한 로그인도 `audit_log`(401, 입력한 이름)에 남는다 → 무차별 시도 감지.
- 로그아웃은 쿠키 삭제. 전원 강제 로그아웃은 `SECRET_KEY` 교체(재배포).

## 3. forecast_app(v2) 게이트
v2는 동료 코드라 앱을 고치지 않고 **Caddy basic_auth**로 감싼다. 사용자 `team`(BASIC_USER), 비밀번호 = APP_PASSWORD(bcrypt 해시는 `entrypoint.sh`가 기동 시 계산). 브라우저가 한 번 인증하면 세션 동안 유지. v2 자체에는 작업자 개념이 없어 **v2 안의 저장(연결·표준화 수정)은 감사 로그가 없다** — 필요하면 다음 단계에서 v2 `app.py`에 이름 입력 + 파일 로그를 추가한다(동료 합의 필요).

## 4. 비밀 관리 규칙
1. `.env`는 각 실행 위치에 하나(로컬 `budget_app/.env`, Compose는 패키지 루트 `.env`). 절대 커밋하지 않는다. `.env.example`만 커밋.
2. 값 생성: `SECRET_KEY` = `py -c "import secrets;print(secrets.token_urlsafe(48))"`; `APP_PASSWORD` = 12자 이상 문구.
3. 전달: 사내 메신저 **비밀 메모/1회성 링크**. 카톡 일반 채팅·이메일 본문 금지.
4. 교체 주기: 팀원 변동 즉시, 그 외 분기 1회. 교체 후 Render 재배포 + 팀 공지.
5. Supabase 연결문자열에는 DB 비밀번호가 들어 있다 — `.env`·Render 환경변수 외에는 어디에도 적지 않는다(문서·이슈·스크린샷 주의).

## 5. 데이터 보관·삭제
- 무료 배포 기간의 실데이터는 **임시**다. 검토 종료 시 Supabase 표를 비우거나 프로젝트를 삭제하고, 사내 서버로 이전한다(배포가이드 §3.3).
- 백업: SQLite 모드는 `budget.db` 1파일, PG 모드는 `pg_dump`. 모델·학습데이터도 같은 DB에 있어 별도 백업 불필요.
- 감사 로그는 삭제 API가 없다(의도). 보존 기간이 필요하면 DB에서 직접 정리.

## 6. 남은 과제(권장 순서)
1. 개인 계정 전환(Supabase Auth 또는 사용자 표) — `audit_log.operator`가 이미 사람 단위라 UI만 바꾸면 된다.
2. 로그인 실패 5회 시 5분 지연(레이트 리밋) — 현재는 기록만.
3. v2 앱 저장 동작의 감사 로그.
4. 사내 이관 후 외부(Render·Supabase) 자원 삭제 확인.
