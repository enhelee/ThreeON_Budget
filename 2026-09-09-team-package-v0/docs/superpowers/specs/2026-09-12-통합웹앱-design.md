## 1. 배경과 목표

### 1.1 지금 무엇이 어색한가

현재 배포는 한 주소(`threeon-budget.onrender.com`) 아래 세 갈래로 나뉘어 있습니다.

| 경로 | 내용 | 프로세스 |
|---|---|---|
| `/` | 소개·문서 사이트 (정적 HTML) | Caddy 직접 서빙 |
| `/app/` | budget_app — 1·2단계 (계획·실적) | uvicorn :8010 |
| `/forecast` | forecast_app — 3·4단계 (표준화·전망) | streamlit :8501 |

사용자가 주소를 열면 **앱이 아니라 문서가 뜹니다.** 작업을 하려면 `/app/`을 따로 알아야 하고, 중장기 전망을 보려면 `/forecast`로 넘어가 **브라우저 기본인증 팝업에 한 번 더** 답해야 합니다. 업무 흐름은 계획 → 실적 → 표준화 → 전망 하나인데 화면은 셋입니다.

### 1.2 목표

**"주소 하나를 열면 로그인하고, 그 안에서 1~5단계와 설정을 좌측 메뉴로 오간다."**

최종 상태에서는 프로세스도 하나(uvicorn)만 남습니다. Caddy·supervisord·Streamlit은 Phase 6에서 제거됩니다.

### 2.2 가장 중요한 사실 — SPA는 이미 존재한다

`webapp/index.html`은 이미 **8개 뷰를 가진 단일 페이지 앱**입니다.

| 메뉴 | `data-view` | 상태 |
|---|---|---|
| H 홈 | `home` | 구현됨 |
| 1 예산 계획 | `budget` | 구현됨 |
| 2 실적 집계 | `collect` | 구현됨 |
| 3 지사 분석 | `branches` | 구현됨 |
| 3+ 실적분석(상세) | `detail` | 구현됨 |
| 4 통계·내보내기 | `stats` | 구현됨 |
| **5 중장기 전망** | `forecast` | **"(준비 중)" 플레이스홀더** |
| S 설정 | `settings` | 구현됨 |

**따라서 이 프로젝트는 "처음부터 다시 만들기"가 아닙니다.** 백엔드 51개 라우트, 도메인 로직 5,777줄, 테스트 87개는 그대로 자산입니다. 다시 짜는 것은 (a) 149KB 단일 HTML이라는 프론트 골격과 (b) 소개·앱·전망이 분리된 배치, 두 가지입니다.

## 3. 목표 아키텍처

### 3.1 Phase 5 시점 (전망 흡수 전)

```
컨테이너 1개
├─ Caddy :8080                         ← 역할 축소 (39줄 → 약 15줄)
│    /forecast*  → :8501  + forward_auth → :8010 /api/auth/status
│    그 외 전부   → :8010
├─ uvicorn :8010   FastAPI
│    GET  /           → SPA (Vite 빌드)
│    GET  /assets/*   → 정적 산출물 (해시 파일명)
│    GET  /app/*      → 301 → /              (팀원 북마크 보호)
│    /api/*           → 기존 51개 라우트 (무수정)
│    GET  /healthz
└─ streamlit :8501   forecast_app
```

### 3.2 Phase 6 완료 시점 (최종)

```
컨테이너 1개
└─ uvicorn :8010   FastAPI   ← 프로세스 하나
     GET  /  ·  /assets/*  ·  /api/*  ·  /healthz
```

Caddyfile · supervisord.conf · forecast/ 폴더가 **삭제**됩니다. 사내 서버 이관 시 필요한 것은 파이썬 이미지 하나입니다.

### 3.3 대안 검토 — Caddy를 어떻게 할 것인가

Streamlit이 Phase 5까지 남으므로 경로 라우터가 필요합니다. 남은 선택은 라우터의 **역할 크기**였습니다.

| | 안A **(채택)** | 안B | 안C |
|---|---|---|---|
| | Caddy를 `/forecast` 전용으로 축소 | Caddy 제거, FastAPI가 직접 프록시 | 현행 유지 |
| `/` 서빙 | FastAPI (SPA) | FastAPI | Caddy (정적) |
| Streamlit 연결 | Caddy 2블록 | FastAPI가 WebSocket 프록시 구현 | Caddy |
| Phase 6 후 | **파일 삭제로 끝** | 이미 없음 | 여전히 필요 |
| 위험 | 낮음 | **높음** — Streamlit WS 프록시는 난도·장애 포인트가 큼 | 낮음 |

**안A 채택 사유**: Caddy를 없애려고 WebSocket 프록시를 직접 구현하는 것(안B)은 얻는 것에 비해 위험이 큽니다. 대신 Caddy 역할을 "전망 앱 한 블록"으로 줄여 두면, Phase 6에서 **제거가 삭제 한 번**으로 끝납니다. 즉 제거하는 것이 아니라 **제거 가능한 상태로 만들어 두는** 접근입니다.

### 3.4 배포 플랫폼 — 서버리스가 불가능한 이유

Vercel·Netlify·Cloudflare Pages 등 서버리스는 이 앱의 백엔드를 담을 수 없습니다.

| 서버리스 제약 | 이 앱의 실제 값 | 판정 |
|---|---|---|
| 함수 실행시간 상한 | 분석 1회 **16~19초** | 위험 |
| 요청 본문 크기 | zrfm2.XLSX 1.2MB · 마스터 285KB | 여유 없음 |
| 파일시스템 쓰기 불가 | Excel 산출물·`config/*.json`·`output/` 생성 | **불가** |
| 콜드스타트 | pandas + openpyxl + **scikit-learn + joblib** | **불가** |
| WebSocket 불가 | Streamlit 필수(Phase 5까지) | **불가** |
| 상주 프로세스 불가 | DB 커넥션 풀·모델 레지스트리 | **불가** |

**결론**: 상주 컨테이너가 필요합니다. Render를 유지하되, Phase 6에서 프로세스가 하나가 되면 어느 컨테이너 호스트에나 올라가므로 플랫폼 종속이 사라집니다. 최종 목적지가 사내 서버이므로 이것이 올바른 방향입니다.

> 참고: Fly.io·Railway·Koyeb 등의 무료 한도는 최근 수년간 계속 변경되어 왔습니다. 이 문서는 특정 조건을 단정하지 않으며, 대안이 실제로 필요해지는 시점에 각 서비스의 현행 요금 페이지를 확인합니다.

### 4.3 URL 설계 — 해시 라우팅

| 주소 | 화면 | 로그인 |
|---|---|---|
| `/` | 게이트 (제목+소개+로그인) | 불필요 |
| `/#/home` | **메인 대시보드** | 필요 |
| `/#/plan` | 1 예산 계획 | 필요 |
| `/#/collect` | 2 실적 집계 | 필요 |
| `/#/branches` · `/#/detail` | 3 / 3+ 분석 | 필요 |
| `/#/stats` | 4 통계·내보내기 | 필요 |
| `/#/forecast` | 5 중장기 전망 | 필요 |
| `/#/settings` | S 설정 | 필요 |

**해시 라우팅을 쓰는 이유**: 현재 SPA는 `state.view` 변수만 바꾸므로 새로고침하면 홈으로 돌아가고, 뒤로가기·북마크·화면 링크 공유가 되지 않습니다. 해시 라우팅은 서버 설정 없이 이를 해결하며, 정적 서빙과도 충돌하지 않습니다.

`/app/*`는 `/`로 **301 영구 이동**시켜 팀원이 저장해 둔 북마크를 보호합니다.

### 4.4 메인 대시보드 (`/#/home`)

위에서 아래로 네 덩어리입니다.

**(1) 헤더 스트립** — 제목, 단계 ①~④, 기준일·rev, 단위(천원/원). 설명이므로 고정 문구.

**(2) 현황 카드 — 실데이터**

`/api/overview`가 이미 연도별 `계획 / 실적 / 집행률 / 실행일시`를 손익·자본으로 나누어 반환합니다. **새 API 없이 그대로 씁니다.**

| 카드 | 출처 |

| 2025 손익 계획 대비 실적 · 집행률 | `GET /api/overview` |
| 2025 자본 계획 대비 실적 · 집행률 | `GET /api/overview` |

| DB 종류 · 인증 상태 | `GET /healthz` |
| 최근 분석 일시 | `GET /api/overview` |

**(3) STAGE 01~04 카드** — 각 카드가 곧 이동 버튼입니다. STAGE 01 → `#/plan`, STAGE 04 → `#/forecast`. 사이드바와 동일하게 동작하므로 처음 쓰는 사람이 어디로 가야 할지 헤매지 않습니다.

**설계 원칙: 하드코딩하는 것은 설명 문구뿐이고, 숫자는 전부 DB에서 끌어옵니다.** 메인을 열 때마다 현재 상태가 찍히므로, 사내 이관 논의 때 화면 하나만 띄우면 됩니다 — 이것이 §1.3의 "실증" 요구에 대한 답입니다.

### 5.2 회귀 방지 원칙 — 쪼개기와 고치기를 분리한다

현재 149KB 안에는 **이미 정상 동작하는 렌더러 8개**가 있습니다. 옮기면서 동시에 개선하면 문제가 생겼을 때 "원래 그랬는지, 옮기다 깼는지"를 구분할 수 없습니다.

1. **Phase 1은 기계적 분할** — 로직을 한 줄도 바꾸지 않고 파일 위치만 옮깁니다.
2. 옮긴 직후 브라우저로 8개 화면을 전부 열어 **기존과 동일한지 실측**합니다.
3. 동일함이 확인된 **뒤에** 게이트 화면·메인 대시보드 같은 변경을 얹습니다.

같은 이유로 **Phase 1에서는 백엔드를 건드리지 않습니다.** `server.py` 1,188줄을 라우터별로 분리하는 것은 분명한 이득이지만, 프론트 이관 중에 백엔드까지 흔들면 회귀 위험이 곱으로 늘어납니다. **87 passed를 기준선으로 고정**하고 진행합니다. 백엔드 분리는 Phase 6 이후 별건으로 둡니다.

### 9.4 6-3이 관문인 이유

설계서 §5가 명시적으로 경고한 지점입니다.

> **3번이 게이트입니다.** 23년 역산이 수기 분석본과 맞지 않으면 표준금액 정의(분모·중위수·절사)를 먼저 고쳐야 하고, 그 상태로 4단계에 넘어가면 오차가 10개년에 누적됩니다.

23년 수기 분석본(손익 −0.06% 검증본)이 있으므로, **23년만으로 산출한 벤치마크로 23년 실적을 역산**했을 때 지사별 오차가 임계 안에 드는지가 통과 조건입니다. 여기서 막히면 6-4 이후를 진행하지 않습니다.

### 9.5 차단 사항 회피

설계서 §6.1은 "정비등급 조인 키(설비ID ↔ 사업장코드 ↔ 처지사) 미정 — **차단 사항**"으로 남겨 두었습니다.

**Phase 6은 v2 방식(지사 단위 `site_year_grade.csv`)을 그대로 승계하므로 이 항목에 막히지 않습니다.** 설비 단위 해상도로 올리는 개선은 CMMS(ThreeON Maintenance) 연동이 필요하므로 범위 밖으로 둡니다(§10).

**통과 기준**: 3·4단계 산출이 v2 결과와 일치 · 23년 역산 회귀 통과 · `docker ps`에 프로세스 하나 · Caddyfile·supervisord.conf·forecast/ 부재 · 전체 테스트 통과.
