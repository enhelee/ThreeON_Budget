## 2. 계산 동일성의 증명 방식

「v2 와 같은 계산」은 말이 아니라 **v2 테스트를 옮겨 실행**하는 것으로 증명한다. 함수 이름·인자·반환 컬럼을 v2 와 같게 두었기 때문에 테스트가 import 한 줄만 바꿔 그대로 돈다.

| v2 테스트 | 개수 | 옮긴 곳 | 옮긴 개수 | 남긴 것 |
|---|---|---|---|---|
| `tests/test_standardization.py` | 21 | `app/tests/test_benchmark.py` | 15 | 파일 IO·엑셀 import 6개 |
| `tests/test_longterm_forecast.py` | 29 | `app/tests/test_forecast_calc.py` | 18 | 파일 IO 4개 · 엑셀 파서 6개 · 테스트예산 1개 |

남긴 것 중 **파일 IO 테스트는 6-5 에서 DB 판으로 다시 썼다**(`app/tests/test_forecast_store.py`, 23개). 엑셀 파서 테스트는 파서를 옮기는 6-6 에서 따라간다.

## 3. 과목 집합과 별칭 — 두 앱의 차이

v2 `builtin_categories` 와 budget_app `config_store.SEED_ITEMS` 는 세 과목만 다르다.

| 어디에만 있나 | 과목 |
|---|---|
| budget_app 만 | `수선유지비-비저장품(보수자재)` · `수선유지비-소모품(자재공기구)` |
| v2 만 | `외주비-기타` |

**셋 다 실제 ERP 자료(zrfm2 43,840행·과목 15종)에 0건**이라 결과가 달라지지 않는다(실측 2026-09-19). 그래서 **budget_app 구성을 정본**으로 삼고 `benchmark.PROFIT_LOSS_ACCOUNTS / CAPITAL_ACCOUNTS` 가 `SEED_ITEMS` 에서 나온다. `forecast_calc` 는 `benchmark` 의 상수를 다시 가져다 쓴다 — 두 모듈이 어긋날 길을 만들지 않기 위해서다. 별칭은 두 앱이 동일하다.

⚠ `forecast_calc.INVESTMENT_ACCOUNTS` 에는 v2 그대로 `외주비-기타` 가 남아 있다. 구성 밖 과목이라 `normalize_item` 뒤에는 절대 매칭되지 않는다 — 무해하지만 v2 와 나란히 비교하기 위해 지우지 않았다.

## 4. 상태 9종 — 파일에서 표로 (6-5 에서 확정)

v2 는 상태를 **CWD 상대경로 CSV** 로 두었다. `BASE_YEAR = 2026` 이 상수라 그 상태는 사실상 「26년 기준 전망의 가정 한 벌」이다.

### 4.1 결정 — 전부 전망 기준연도 축 (사용자 결정 2026-09-19)

세 안 중 ①을 택했다.

| 안 | 내용 | 판정 |
|---|---|---|
| ① **전부 `base_year` 축** | 표 9개 모두 기준연도마다 완전한 한 벌. ＋연도 = 직전 복사 | **채택** — 연도별 기준정보(`dept_config`)와 같은 모델. 27년 전망을 시작해도 26년 가정이 남아 「무엇이 달라졌나」가 보인다 |
| ② 정비등급·돌발사업만 연도, 나머지 단일 벌 | v2 그대로 | 27년 전망 시작 시 팩터·수정값·본사배분이 덮여 사라짐. 나중에 축을 붙이려면 표를 다시 만들어야 함 |
| ③ 정비등급만 공용, 나머지 `base_year` | 등급 이력은 「사실」이라 누적 | 미래 연도 정비 「계획」도 기준연도별로 바뀌어 경계가 흐림 |

두 연도 축의 이름을 고정한다.

- **`base_year`** — 어느 해에 세운 전망인가(«26년 기준»). 문자열 `'2026'`. 표 9개 전부의 PK 첫 컬럼.
- **`연도`** — 정비·사업의 대상연도. 2026년 기준 전망 안에 «2027년 TI 정비»가 있다. `site_grade`·`forecast_hot_parts`·`hq_temp`·`forecast_surprise` 에만 있다.

### 4.3 입출력 계약

- `forecast_store.load_*(conn, base_year)` 는 **v2 `load_*()` 가 돌려주던 것과 같은 컬럼·dtype** 의 DataFrame 을 돌려준다(사업장 `str`, 연도 `int`, 금액·비율 `float`, 활성 `bool`). 그래야 `benchmark.compute_standard_amounts`·`forecast_calc.compute_all_sites` 에 그대로 들어간다. `test_forecast_store.py` 가 표마다 이를 고정한다.
- `save_*(conn, base_year, df)` 는 그 기준연도 한 벌을 **통째로 갈아 끼우고** 저장된 모양을 다시 읽어 돌려준다. 다른 기준연도는 건드리지 않는다. 같은 키가 겹치면 뒤의 것이 이긴다.
- `append_hq_temp_project`·`append_surprise_project` 는 v2 와 같은 인자 순서에 `(conn, base_year, …)` 가 앞에 붙는다.
- `copy_base_year(conn, from, to)` — 아홉 표 전부 복사, 대상은 먼저 지움. `base_year_is_untouched` 가 `copy-year` 409 가드의 짝이다(팩터 시드만 있는 상태는 「손대지 않음」).
- `import_v2_csv_dir(conn, base_year, dir)` — v2 실행 폴더의 CSV 를 한 기준연도로 들여온다. **6-8(Streamlit 삭제) 전에 동료 PC 상태를 넘기는 유일한 길**이다.

### 4.4 계산부에 생긴 한 가지 변경

`forecast_calc.hq_amount_by_site_account` 는 v2 에서 `26년예산` 열만 제외했다. 기준연도가 파라미터가 되면 열 이름이 `27년예산` 으로 바뀌므로 정규식 `^\d{2,4}년\s*예산$` 으로 본다(`is_hq_master_site_col`). 그대로면 27년예산 열이 지사로 잡혀 본사 배분 합계가 두 배가 된다. v2 테스트 18개는 그대로 통과한다.

## 5. 지사 표시명·유형 해석 — `mapping_config` 대체

v2 는 예산계획의 부서코드(6~7자리)와 실적의 손익센터(4자리)를 지사명으로 풀기 위해 `site_type_map.csv`(표시명·지사유형) → `dept_code_master.csv`(부서코드) → 접두사 매칭 → `미매핑(NNN0번대)` 순으로 봤다. budget_app 에는 같은 정보가 이미 연도별 표로 있다.

| v2 층 | budget_app 대체 |
|---|---|
| `site_type_map.csv` 표시명 | `dept_config(year)` 의 지사 이름 — 실측으로 v2 표시명 24개와 동일 |
| `site_type_map.csv` 지사유형·적용시작연도 | `dept_config(year)` 의 그룹 — 연도 축이 이미 있어 「적용시작연도」가 필요 없다(양산지사 2023 DH → 2025 중대형CHP) |
| `dept_code_master.csv` | `dept_master(year)` 의 부서코드→처지사(`db.load_deptcode_map`, 없는 해는 가장 가까운 과거 연도) |
| 접두사 매칭 | `_best_prefix_match` — 자릿수 무관, 최소 3자리 |

6-4 가 `forecast_calc.get_site_display_name`·`get_current_site_type` 을 **모듈 수준 훅**(기본 항등/«미매핑»)으로 남겼고, 6-5 의 `forecast_store.bind_site_resolvers(conn, year)` 가 계산 직전에 이 둘을 갈아 끼운다. 순수계산 안에 숨은 DB 읽기를 두지 않기 위한 구조다 — 테스트는 v2 처럼 monkeypatch 로 돈다.

## 6. 6-6 에서 한 것 (설계 [2026-09-19-Phase6-6-전망탭-design.md](2026-09-19-Phase6-6-전망탭-design.md))

- **`BASE_YEAR`·`FORECAST_YEARS` 파라미터화 완료** — `forecast_years(base_year)` · `year_multiplier(…, base_year)` · `compute_site_table/compute_all_sites(…, base_year, years)`. 기본값 2026 이라 v2 승계 테스트는 그대로다.
- **계산부 변경 하나 더(§4.4 에 이어)** — 등급 이력이 없는 지사에서 `compute_site_table` 이 표준금액을 0 으로 쓰던 것을 등급 «표준» 행으로 물러서게 했다. v2 는 지사 목록이 등급 이력에서 나와 이 경로가 없었고, 여기서는 지사가 `dept_config` 에서 오므로 등급 없는 지사가 정상 입력이다(실데이터가 그 상태).
- **엑셀 파서 4종 승계**(`forecast_import.py`) — 정비등급 이력·정기점검 일정·고온부품·본사배분. 시트명 매핑은 `dept_config` 지사명, 단위 천원(v2 의 ×1000 제거). v2 의 실적·예산계획 import 는 Test 모드용이라 옮기지 않았다(설계서 §9.2).
- **입력 조립**(`pipeline_forecast.py`) — 실적 = **마감된 연도**의 최신 분석 결과 `biz_line`(구분 계획집행·신규·신규(소액집행)), 당해년도 예산 = 1단계 계획본 `plan_row`(어댑터가 v2 열 이름으로), 지사 = `dept_config(base_year)` 포함 지사 중 본사 제외. 사용자 결정 2026-09-19.
- **API**(`api_forecast.py`, 7개 경로) 와 **SPA 5번 탭**(`views/forecast.js` + `forecast_actions.js`) — 기준연도 선택기 + 하위 탭 3개. `FORECAST_URL`·`/healthz.forecast_url` 제거. 엑셀 **내보내기**는 6-7.

## 7. 동료분 최종 확인 (6-1 Step 3) — **미완**

설계서 §1.3 의 포팅 동의는 2026-09-12 자다. 그 뒤 v2 가 바뀌었을 수 있으므로 **6-8(Streamlit·Caddy·supervisord 삭제) 전에** 다음을 확인받는다.

1. §1 의 판정(대체·삭제 대상 포함)에 이견이 없는지 — 특히 `template_fill.py`(손익·자본 집계표)를 budget_app 내보내기로 대체한 것
2. §4.1 의 기준연도 축 결정 — v2 화면 사용 습관과 맞는지
3. 동료 PC 의 v2 실행 폴더 CSV 를 `import_v2_csv_dir` 로 넘겨 받을지, 언제 받을지
4. **총원가 배분 시트(6-7)** — 지사(천원) 블록에 «지사탭 기준연도 값 − 본사배분 몫»을 넣고 본사·전체 블록은 양식의 수식에 맡겼다. v2 는 여섯 블록을 합산값(백만원)으로 덮어썼다. 재무팀이 보던 결과와 다를 수 있으니 한 번 대조
5. 내장 양식은 «26년» 라벨이 박힌 2026년 기준 양식 — 27년 기준 전망을 낼 때 재무팀 새 양식을 같은 형식으로 받을 수 있는지
