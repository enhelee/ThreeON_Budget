# 설계 — 연도별 기준정보를 DB로: 구성·마스터·마감 해제 워크플로

> 작성 2026-09-15 · 기준 구현 rev17(테스트 107 passed) · 배포 `threeon-budget.onrender.com`
> 상위 문서: [2026-09-12-통합웹앱-design.md](2026-09-12-통합웹앱-design.md) — Phase 0~5 완료, Phase 6(전망 흡수) 미착수
> 이 문서는 그 Phase 6과 **독립적으로** 진행할 수 있는 별건입니다. 다만 "파일 상태를 DB로 옮긴다"는 방향이 같아, Phase 6이 전망 앱 상태를 옮길 때 여기서 만든 패턴을 그대로 씁니다.

---

## 1. 왜 지금인가

### 1.1 배포된 앱이 틀린 값으로 집계하고 있다

2026-09-15 배포 확인 중에 드러났습니다. 4번 통계의 「지사그룹별」이 이렇게 나옵니다.

| 그룹 | 배포 현재 | 실제 기준 |
|---|---|---|
| 중대형CHP | 33,606,101 | **35,579,300** |
| DH | 13,390,495 | **11,417,296** |

차이는 양산지사 하나입니다(2025년 손익 계획 1,973,199 · 실적 3,862,767천원). **양산지사는 2023년에 발전설비 건설 중이라 공식적으로 DH지사였고, 준공 후 중대형CHP지사가 되었습니다.** 두 값이 다 맞습니다 — 연도가 다를 뿐입니다.

### 1.2 뿌리 — 기준정보에 연도 축이 없다

앱은 지사 구성을 `config_store._SEED_DEPTS`에서 읽는데, 이것이 **연도 구분 없는 목록 하나**입니다.

```python
# src/budget/config_store.py:13
"DH": ["중앙지사", "고양사업소", ..., "양산지사", "평택지사"],
```

연도별 파일(`지사구성_2025.json`)이 이 한계를 덮고 있었지만, 그 파일은 `.gitignore`·`.dockerignore` 양쪽에 걸려 **저장소에도 이미지에도 없습니다.** 개발자 PC에서만 덮이고 배포에서는 시드가 그대로 드러납니다.

준공·이관처럼 지사의 성격이 바뀌는 사건은 실제로 일어납니다. 매년 한두 건이라 그동안 손대지 않아도 지나갔을 뿐입니다. 연도 축은 편의가 아니라 **정확성의 요건**입니다.

### 1.3 같은 문제가 마스터에도 있다

| 항목 | 지금 어디에 | 연도 축 |
|---|---|---|
| 지사 구성 | 파일 `지사구성_{연도}.json` | 파일명에 있음 |
| 과목 구성 | 파일 `과목구성_{연도}_{손익\|자본}.json` | 파일명에 있음 |
| 예산과목·처지사 별칭 | 파일 | 없음 |
| 예산과목 마스터 | DB `item_master` 457행 | **없음** |
| 부서코드 마스터 | DB `dept_master` 83행 | **없음** |
| 학습 매핑 | DB `learned_match` 10,888행 | 없음 |
| 모델 레지스트리·학습데이터 | DB `model_registry`·`training_example`·`training_snapshot` | 없음 |

마스터는 이미 DB에 있지만 **연도 구분이 없습니다.** 조직개편이 있으면 부서코드↔처지사 대응이 바뀌고 예산코드 체계도 손질되는데, 지금 구조로는 그때마다 과거가 함께 덮입니다.

모델 레지스트리와 학습데이터는 이미 DB이므로 이 작업의 대상이 아닙니다.

### 1.4 고칠 방법이 화면에 없다

지사그룹은 4번 통계의 막대에만 나타나고, **어디서도 볼 수 없고 고칠 수 없습니다.** 지금 바꾸려면 개발자 PC의 JSON을 고쳐 재배포해야 합니다. 팀이 쓰는 도구로서 성립하지 않습니다.

## 2. 목표

**"그 해의 기준을 그 해에 저장하고, 화면에서 고치고, 마감으로 잠근다."**

|---|---|

- 전망 앱 상태의 DB 이전 — Phase 6

## 3. 데이터 모델

### 3.1 표 다섯 개

```
dept_config  (year, 이름, 그룹, 포함, 순서)                                PK(year, 이름)
item_config  (year, budget, 과목, 대분류, 심의대상, 포함, 실적반영, 순서)    PK(year, budget, 과목)
item_master  (year, 예산코드, 예산과목, 주관부서코드, 주관부서명, 속성, 비고)  PK(year, 예산코드)
dept_master  (year, 부서코드, 부서명, 처지사, 비고)                        PK(year, 부서코드)
alias        (종류, 원표기, 정규표기)                                      PK(종류, 원표기)
```

앞의 넷은 `year`가 기본키의 일부입니다. **연도마다 완전한 한 벌**이 들어 있어, 2023을 열면 그 해 기준이 그대로 나옵니다.

`alias.종류`는 `item` 또는 `dept`입니다.

### 3.2 왜 완전 사본인가

세 가지 안을 검토했습니다.

| | 완전 사본 **(채택)** | 기준 세트 + 차이 | 유효기간 |
|---|---|---|---|
| 저장 | 연도마다 한 벌 | 기본 + 변경분 | 항목마다 구간 |
| 과거 재현 | **그대로 보존** | 기준을 고치면 소급해 흔들림 | 보존됨 |
| 읽기 | 단순 조회 | 병합 필요 | 구간 질의 |
| 편집 화면 | **표 하나** | 무엇이 상속인지 표시 필요 | 구간 쪼개기·붙이기 |

**채택 사유**: 지사 24행·과목 8~11행 수준이라 중복 저장이 부담되지 않습니다. 다른 두 안이 해결하는 문제(중복)가 이 규모에서는 존재하지 않는 반면, 그 대가인 복잡도는 그대로 치러야 합니다.

과거 재현성이 결정적이었습니다. 2023년 분석을 다시 돌릴 때 그 해 기준이 남아 있어야 하는데, 완전 사본은 그것이 공짜로 따라옵니다.

"매년 조금씩만 바뀐다"는 성질은 **저장 구조가 아니라 생성 시점**에서 다룹니다 — `+연도`가 직전 연도를 복사합니다(§6.3).

### 3.3 마이그레이션

| 대상 | 방법 |
|---|---|
| `item_master` 457행 · `dept_master` 83행 | 기존 연도(2023·2025) **각각에 같은 내용으로 복사** |
| 별칭 파일 | `alias` 표로 1회 이관(연도 없음) |
| 지사·과목 구성 | 파일을 이관하지 않고 **연도별 시드로 심는다** — §4.1 |

**이관의 성공 기준은 "동작이 하나도 바뀌지 않는 것"입니다.** 마스터를 모든 기존 연도에 복사하면 이관 직후 어느 연도를 열어도 지금과 같은 결과가 나오고, 그 다음부터 연도별로 갈라집니다.

## 4. 초기값

### 4.1 연도별 시드를 코드에 둔다

`_SEED_DEPTS`를 연도별 구조로 바꿉니다.

```python
_SEED_DEPTS = {
    "2023": {"본사": [...], "중대형CHP": [...], "소형CHP": [...], "DH": [..., "양산지사", ...]},
    "2025": {"본사": [...], "중대형CHP": [..., "양산지사"], "소형CHP": [...], "DH": [...]},
}
```

DB에 그 연도 구성이 없으면 시드를 심습니다. 시드에 없는 연도는 가장 가까운 과거 연도의 시드를 씁니다.

**왜 파일 이관이 아니라 코드 시드인가.** 지사 구성 JSON은 개발자 PC에만 있고 저장소·이미지 어디에도 없습니다(§1.2). 로컬에서 운영 DB로 스크립트를 쏘면 지금 배포는 고쳐지지만, 사내 서버·새 개발자 PC 등 **다른 환경은 여전히 빈 상태로 시작**합니다. 시드를 코드에 두면 어느 환경에서든 첫 기동만으로 옳은 값이 됩니다.

시드는 "그 연도를 처음 만들 때의 출발점"일 뿐이고, 이후 편집은 전부 DB에서 일어납니다. 한 번 심은 뒤에는 시드를 고쳐도 기존 연도에 영향이 없습니다.

### 4.2 양산지사

**2025년 양산지사는 중대형CHP입니다**(사용자 확인 2026-09-15). 2023년은 DH를 유지합니다. 이 두 줄이 §1.1의 집계 오차를 없앱니다.

### 4.3 과목 구성 시드

기존 `SEED_ITEMS`(손익 8·자본 11)를 연도별 구조로 감쌉니다. 현재 2023·2025 모두 같은 내용이므로 두 연도에 동일하게 심습니다.

### 4.4 미확인 — 2023년 손익 과목 2건의 심의대상

개발자 PC의 `과목구성_2023_손익.json`과 코드 시드가 두 과목에서 갈립니다.

| 과목 | 코드 시드 | 로컬 파일 |
|---|---|---|
| 수선유지비-건물/구축물 | 심의대상 **켜짐** | 꺼짐 |
| 수선유지비-열원보완개선및기타 | 심의대상 **켜짐** | 꺼짐 |

이 두 과목은 프로젝트 기준상 심의대상(임계값 50,000천원 이상 분리)으로 확정된 것들이라 **시드(켜짐)가 맞다고 보고 그대로 심습니다.** 로컬 파일의 꺼짐은 특정 시점의 임시 조정이었을 가능성이 큽니다.

2023년이 실제로 달랐다면 4번 단계 이후 화면에서 고칠 수 있습니다. 다만 그 해가 이미 마감되어 있다면 해제 → 수정 → 재마감이 필요하므로, **이관 전에 확인해 두는 편이 낫습니다.**

### 4.5 별칭은 연도 축에서 뺀다

별칭은 `경남지사(양산RPS 태양광) → 양산지사`처럼 **같은 대상을 가리키는 다른 표기**를 정리하는 장치입니다. 표기 흔들림은 연도가 바뀐다고 무효가 되지 않고, 오래된 표기가 몇 년 뒤 자료에 다시 나타나기도 합니다. 연도로 쪼개면 같은 별칭을 매년 다시 입력해야 하는데 얻는 것이 없습니다.

## 5. 읽기 경로

### 5.1 config_store 교체

`config_store`의 시그니처를 바꿉니다.

```
load_dept_config(config_dir, year)  →  load_dept_config(conn, year)
load_item_config(config_dir, year, budget)  →  load_item_config(conn, year, budget)
load_item_alias(config_dir)  →  load_item_alias(conn)
load_dept_alias(config_dir)  →  load_dept_alias(conn)
save_*  동일하게 conn 기반
```

호출부는 `classify` · `matching` · `plan_summary` · `pipeline_plan` · `pipeline_actual` · `pipeline_db` · `server.py`인데, **모두 이미 `conn`을 들고 있어 인자만 바뀝니다.** 파일 IO 코드는 삭제합니다.

### 5.2 함께 사라지는 것

- `CONFIG_DIR` 환경변수(Dockerfile · docker-compose · .env.example)
- `entrypoint.sh`의 구성 복사 루프 — Phase 5에서 넣었으나 복사 대상이 애초에 없던 코드입니다
- `app/config/*.json`과 그 `.gitignore`·`.dockerignore` 항목

## 6. 화면

### 6.1 설정 탭 — 「연도 기준정보」

대상연도 기준으로 네 가지를 편집합니다.

| 탭 | 편집 |
|---|---|
| 지사 구성 | 그룹 선택(본사/중대형CHP/소형CHP/DH) · 포함 체크 · 순서 |
| 과목 구성 | 대분류 · 심의대상 · 포함 · 실적반영 체크 (손익/자본 전환) |
| 예산과목 마스터 | 조회 + 엑셀 업로드(기존 업로드 재사용, 연도 지정) |
| 부서코드 마스터 | 조회 + 엑셀 업로드 |

별칭은 연도와 무관하므로 **공통 섹션**으로 따로 둡니다.

### 6.2 API

```
GET    /api/config/depts?year=          PUT /api/config/depts     {year, rows}
GET    /api/config/items?year=&budget=  PUT /api/config/items     {year, budget, rows}
GET    /api/config/alias                PUT /api/config/alias     {종류, rows}
GET    /api/master/items?year=          (업로드는 기존 라우트에 year 추가)
GET    /api/master/depts?year=
POST   /api/config/copy-year            {from_year, to_year}
```

변경 요청은 기존 미들웨어가 감사 로그에 남깁니다.

### 6.3 새 연도

`+연도`는 지금 빈 연도를 만듭니다. 앞으로는 **직전 연도의 구성·마스터를 복사**해 만듭니다(`/api/config/copy-year`). 복사할 이전 연도가 없으면 시드를 씁니다.

## 7. 마감 해제 워크플로

### 7.1 지금의 문제

마감(`year_lock`)은 업로드·분석·재배정·수정을 차단하고 그 시점 산출물 6종을 `output/마감/{연도}/`에 보관합니다. 그런데 **해제는 버튼 한 번이면 끝이고, 열려 있다는 사실이 설정 화면 안쪽 배지 외에는 어디에도 드러나지 않습니다.** 마감 연도의 숫자는 대외 보고에 쓰인 값일 텐데, 열린 줄 모르고 며칠이 지날 수 있습니다.

### 7.2 여는 순간부터 닫는 순간까지 감싼다

| 시점 | 동작 |
|---|---|
| **해제** | "이 연도는 마감된 값입니다. 여시겠습니까?" 확인 + **해제 사유 한 줄** 입력 → 감사 로그 |
| **열린 동안** | **모든 화면 상단에 배너** — `⚠ 2023년이 마감 해제 상태입니다 · 작업이 끝나면 다시 마감하세요` + 마감 버튼 |
| **재마감** | 열린 동안의 **변경 요약**을 보여주고 승인 → 감사 로그 |

배너는 다른 연도를 보고 있어도 나타납니다. 그 연도가 열려 있다는 사실을 잊는 것이 정확히 막으려는 상황이기 때문입니다.

변경 요약은 `구성 2건 · 재배정 5건 변경 · 분석 1회 재실행` 형태로, 해제 시각 이후의 `override`·`biz_edit`·`biz_delete`·`manual_biz`·구성 변경·`run`을 셉니다.

### 7.3 마감된 연도의 구성은 못 고친다

기존 `_guard_unlocked`를 구성·마스터 변경에도 적용합니다. 과거 기준을 고치려면 마감을 풀어야 하고, 풀면 배너가 뜹니다. 이것이 의도된 마찰입니다.

## 8. 분석 반영 연동

구성·마스터 변경을 기존 `분석 반영 (N)` 배지에 포함시킵니다(`/api/pending`).

**왜 별도 알림이 아닌가.** 사용자 입장에서 "결과에 반영되지 않은 변경"이라는 점이 재배정·수정과 완전히 같습니다. 알림을 두 갈래로 나누면 어느 것을 눌러야 하는지 헷갈립니다.

자동 재분석은 택하지 않았습니다. 분석이 16~19초 걸리므로 구성 한 줄 고칠 때마다 기다리게 되고, 여러 줄을 연달아 고치는 상황에서 특히 나쁩니다.

## 10. 순서

| # | 작업 | 이 단계가 끝나면 |
|---|---|---|
| 1 | DB 표 5개 + 마이그레이션 | 데이터가 연도별로 자리 잡음 |
| 2 | 연도별 시드 (**2025 양산지사 중대형CHP**) | **§1.1의 집계 오차가 사라짐** |
| 3 | `config_store` DB 전환 · 파일 IO 제거 | 배포 환경과 개발 PC가 같은 값으로 동작 |
| 4 | 설정 화면 「연도 기준정보」 | 팀이 직접 고칠 수 있음 |
| 5 | 마감 해제 워크플로 + 전 화면 배너 | 열린 상태가 드러남 |
| 6 | `+연도` 복사 | 새 해 준비가 한 번으로 끝남 |

**2번까지만 끝나도 지금 틀어져 있는 집계가 바로잡힙니다.** 나머지는 그 위에 얹는 개선입니다.
