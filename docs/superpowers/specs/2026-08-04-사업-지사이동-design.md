# 사업 통째 지사 이동 (예산귀속 처.지사 변경) — 설계

작성일 2026-08-04 · 상태: 승인됨(사용자 확정)

## 배경

상세 화면(③+ 실적분석)의 ✎ **사업 내용 수정** 폼은 사업명·속성·**주관부서명**·부서부만 고칠 수 있다.
그런데 종합표와 지사별 집계의 기준은 **처지사(예산귀속 지사)** 이고, 주관부서명은 단순 표기 텍스트다.
그래서 사용자가 "이 사업을 미래사업처에서 플랜트기술처로 옮기고 싶다"며 주관부서명을
플랜트기술처로 고쳐도 집계는 그대로여서, 삭제 후 재생성해야 하는 것으로 오해하기 쉽다.

실제로 지사 이동 기능은 이미 있다 — 전표 트리를 펼쳐 `전체 선택` 후 재배정 바의
`이동할 지사`(`override.target_dept`)를 쓰면 된다. 다만 (a) 발견하기 어렵고,
(b) 전표만 옮기므로 **계획행의 연예산(A)은 옛 지사에 남는다**.

## 목표

✎ 폼에서 지사를 바꿔 저장하면 **그 사업이 통째로**(연예산 + 귀속 전표) 새 지사로 옮겨진다.
삭제·재생성 없이, 되돌릴 수 있게.

## 원리 — 기존 저장소 두 개를 동시에 쓴다

| 옮길 대상 | 저장 위치 | 적용 시점 |
| --- | --- | --- |
| 계획행(연예산 A) | `biz_edit` 의 `fields.처지사` | 매칭 **전** `plan_df` 패치 (`pipeline_actual.run_actual_frames`) |
| ERP 전표(실적 B) | `override.target_dept` (기존 기능) | 매칭 **전** `depts_norm` 바꿔치기 (`matching`) |

둘 다 매칭 **전에** 적용되므로 계획행과 전표가 새 지사에서 다시 만나
`계획집행` 관계와 매칭확신도가 유지된다. 총액 보존식
(`종합표 총액 + 미반영 + 타예산 = ERP 전체`)도 불변이다 — 어느 쪽도 금액을 만들거나 없애지 않고
귀속만 바꾸기 때문이다.

새 테이블 없음. 파이프라인 로직 변경 없음(`biz_edit` 적용부가 이미
"`plan_df` 컬럼이면 무엇이든 대입"하는 일반 구조라 `처지사`가 자동으로 동작한다).

## 변경 사항

### 1. 서버 — `POST /api/biz-edit` (`server.py`)

`allowed` 집합에 `"처지사"` 추가. 그 외 검증·잠금 가드는 그대로.

### 2. DB — `patch_latest_run_biz` (`src/budget/db.py`)

즉시 반영 패치 필드 목록에 `처지사` 추가. 지사가 바뀌면 최신 실행의 `match_line.처지사정규`도
같이 갱신해 화면(전표 트리)이 어긋나지 않게 한다. 영구 반영은 재분석이 담당한다.

### 3. 웹 UI — ✎ 폼 (`webapp/index.html`, `webapp/body.template.html`)

- 폼을 4칸 → 5칸. 맨 앞에 **`예산귀속 지사(처.지사)`** `<select>`(등록 지사 목록,
  현재 지사 기본 선택). 미매핑 가상 지사는 목록에서 제외(`realBranches()`).
- 안내 문구 추가: *"주관부서명은 표기용입니다. 종합표·지사별 집계 기준은 '예산귀속 지사'입니다."*
- 저장(`save-edit`) 분기:
  - **지사 그대로** → 지금과 동일(`/api/biz-edit`만).
  - **지사 변경** → 확인창(사업명, A → B, 연예산 n원 + 전표 m건) 후
    1. 계획행이 있는 사업(구분이 `신규*`/`미매핑`이 아님)이면 `/api/biz-edit` fields에 `처지사` 포함
    2. 그 사업의 전표 전체(`b.전표[].erp_row_id`)를 모아 `/api/override`
       (`target_name` = 최종 사업명, `target_dept` = 새 지사) 1회 호출
    3. 전표가 있었으면 자동 재분석(`runAnalyze(true)`) 후 화면을 **새 지사로 전환**,
       없으면(미시행) 상세만 새로고침
- 전표를 손으로 고를 필요가 없다 — `/api/branch-detail`이 이미 사업별 전표 배열을 내려준다.

`index.html` 은 `<head>`(스타일) + `body.template.html` 본문 구조이므로 두 파일을 동일하게 유지한다.

## 에지 케이스

| 상황 | 동작 |
| --- | --- |
| 미시행(계획행 O, 전표 0) | `biz_edit`만 → 연예산이 새 지사로 이동 |
| 신규(계획행 X, 전표 O) | `override`만 → 새 지사의 신규 사업으로 귀속 |
| 미매핑 가상 지사 행 | `override`만(계획행 없음) — 실제 지사 지정과 동일 경로 |
| 마감(잠금) 연도 | 기존 `_guard_unlocked`가 423으로 차단(✎ 버튼 자체도 숨김) |
| 새 지사가 지사 구성에 없음 | select가 등록 지사만 노출하므로 발생 불가 |

## 되돌리기

설정 탭의 「사업 내용 수정 이력」(처지사 변경 항목)과 「수동 재배정 이력」에서 해당 항목을 삭제하고
재분석하면 원상복구된다. 두 이력 모두 삭제 UI가 이미 있다.
